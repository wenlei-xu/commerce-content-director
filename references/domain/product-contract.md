# Product contract

Resolve exactly one active `products` record directly from the product table by the user's name or ID. A task relationship is not a product lookup substitute.

Required facts are the schema-resolved product status, positioning, core benefits, audience, pain point, scene, interaction capabilities, key structure locks, default anchor, and any detail or scene assets required by the planned shots. Product facts, structure, scale, openings, and interaction paths come only from this record.

When a task selects one to three core benefits, copy only the selected value propositions and their product-record provenance into the task. Do not copy structural mechanics into the benefits field.

For each Job, create `product_asset_plan` from shot risk:

- `default_anchor` is the identity baseline for every relevant Job. When it is the approved multi-view product reference, route only this attachment by default.
- `detail_assets` and `scene_assets` remain source evidence and compatibility fallbacks; do not add them automatically when the approved default anchor already proves the current shot.
- Add a detail or scene asset only when the selected shot has a fact that the default anchor cannot prove and the workflow explicitly records that reason.
- A recurring subject adds a subject anchor without displacing required product evidence.

## Fixed integrated visual structures

If `关键结构锁` declares fixed component positions or a non-interchangeable connection path, record that statement as the Job's `product_visual_lock`. Use a complete clean front-view product anchor that makes the locked components and their relative positions legible; a crop that loses a required component is not a valid anchor for that Job.

For every visible-product first-frame Job, route `product_anchor` in position 1. When both a recurring subject and a structure-replication scene-space reference are routed, their order is position 2 `subject_anchor`, then position 3 `source_scene_reference`. The product reference has identity priority; the subject owns subject identity; the source scene owns only space, camera and light.

Treat the locked components as one product in every planned first frame. Select the pet's bite point, human grip, camera angle and toy orientation so the true connection path remains visible and readable. Do not remove a connected component when an action would obscure it; redesign the contact or framing instead.

Record each asset's schema field, filename, remote token, local hash, role, input position, and segment mapping. Validate bytes, MIME, dimensions, hash, count, and role mapping before submission. Do not infer an opening, loading path, dispensing path, connection, or permitted action from a name, prior output, or model memory.
