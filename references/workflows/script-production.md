# Workflow: script production

本流程以 [script-workbook-contract.md](../domain/script-workbook-contract.md) 为准。创作稿使用 Markdown，是人和 Agent 共同修改的内容中心；执行时产生的 Prompt、请求和结果写入 [execution-record-contract.md](../domain/execution-record-contract.md)。旧 `structured_script` 仅用于历史任务兼容和迁移。

## 进入条件

读取任务语言锁、产品定位、`交互能力`、`关键结构锁`、主体和场景资产。若用户提供了口播原文，原文进入创作稿后锁定；只有用户明确要求改写、优化或重新创作时，才允许修改。若使用脚本库，先复制审核通过模板的完整口播，再做已核实的产品事实替换，并保存差异说明。

创意方向可以锁定内容角度和观看承诺，但不提前规定所有产品的动作链、Beat 顺序或镜头列表。参考视频可以提供可迁移的节奏、空间关系和情绪曲线；它不能带入来源产品、主体、Logo 或未经验证的功能。

## 工作顺序

1. 创建或打开本次 Markdown 创作稿，记录产品、主体、场景、口播来源和语言锁。
2. 口播定稿后生成完整 TTS，再进行 ASR，保留真实时间轴。
3. 根据 ASR、口播含义和动作完整性建立生成段落。每段填写时间、对应口播、画面和必要的衔接状态。
4. 画面描述直接写动作：谁做什么，发生什么变化，产品哪一事实需要看清。不要另建动作导演稿或固定互动计划。
5. 互动模板只在有帮助时查询。可用模板是参考案例；没有合适模板时，根据产品事实写产品衍生动作。产品事实不足以支持安全、可见动作时才停止。
6. 准备首帧时，Agent 读取当前段落、前后衔接、素材和产品锁，直接写首帧 Prompt；保存执行记录后才调用生成工具。
7. 首帧通过后，Agent 观察实际首帧，再写视频 Prompt，描述从进入状态开始的一个主要变化。保存执行记录后提交视频任务。
8. 生成结果回写创作稿对应段落，并在执行记录保存请求、输入素材、模型、结果、状态和审核意见。

## 段落规则

每个段落至少包含：

```markdown
## S02｜6–12 秒

对应口播：...

画面：
主人刚要拿走玩具，狗狗把玩具叼回来，放到自己的垫子上。

衔接：
下一段从玩具在垫子上、狗狗仍在旁边开始。
```

`Beat` 是可选的叙事标记，用于复杂内容的铺垫、转折和回收。它不是动作脚本，也不与 Segment 强制一一对应。简单视频按段落组织即可。

不强制每个段落拥有 Hook、卖点、CTA、互动模板 ID、证明动作或独立机位字段。只有脚本确实需要时才增加“必须看清”。不要把“闻嗅、推动、啃咬、寻食”写成所有产品的默认顺序。

## 口播和画面的关系

口播是音频事实，ASR 提供实际时间。画面应该在口播提到产品、动作或结果时给出足够可见证据；情绪和过渡句不要求逐字对应一个产品特写。一句话可以跨多个视频段落，完整 TTS 不按字幕行拆成多段生成；字幕在最终音频确定后生成。

中文外部 TTS 路径继续由完整 TTS、环境声视频、最终混音和最终 ASR 组成。模型原生对白路径仍按当前 Segment 分配对白，避免模型重复或遗漏台词。

## 批量创作

批量任务先比较每条稿子的开场事件、主体目的、主要动作和结果。只替换产品名、材质、颜色或同义动作词属于重复创意。用户明确要求同一结构适配时可以复用，并保存复用原因；否则让 Agent 重新设计画面事件。`validate_batch_creativity.py` 可作为提示工具，不能代替正文审读。

## 审核与修订

口播审核关注原文锁、事实和生活化表达；画面审核关注动作可执行、产品结构、主体身份、连续性和内容是否具体。提示词审核必须对照当前创作稿段落，指出动作或结果被替换的地方。

修改画面事件会令对应首帧/视频执行记录过期，并触发相邻衔接检查。只修改摄影表达时可更新执行记录，但最终 Prompt 不能与画面事件冲突。只有当前创作稿修订和对应执行记录一致，才允许提交。

## 兼容旧工具

现有 `validate_structured_script.py`、`build_script_package.py`、`render_script_views.py` 和旧生成计划继续服务历史 JSON 任务。新任务不得以它们作为创作入口，不得把旧 `build_packages.py` 的固定 Beat 骨架复制为新脚本。迁移旧任务时，将动作合并到 Markdown 段落，保留旧记录的来源和版本。
