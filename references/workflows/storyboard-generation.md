# Workflow: storyboard generation and script fidelity

Read authority.md, script-contract.md, script-validation.md, product-contract.md, subject-contract.md, product-execution-contract.md, reference-asset-contract.md, image-prompt-contract.md, [storyboard-candidate-contract.md](../storyboard-candidate-contract.md), [flow2api-image-execution.md](../flow2api-image-execution.md) and delivery-contract.md.

Input is one freshly read Feishu script record whose script status is locked and script check status is passed. Its `目标口播语言` and `structured_script.runtime.target_spoken_language` must both match `plan/language-lock.json`. A local script package alone is not sufficient. Read its structured script, accepted product assets, subjects and configuration. Never infer a different creative direction or rewrite the script.

Original and replication modes use the same generation unit. Divide the locked target duration into configured 10-second target production Segments. Each Segment generates complete 2×2 boards containing four 9:16 panels. Successful boards remain backend candidates until they are assembled into one or more complete storyboard versions. A human approves a complete version, not an isolated Segment. Source-video narrative segments, selected evidence frames and reference timestamps do not alter the target production segmentation.

1. Run the workflow-scoped preflight with the locked spoken language, fresh-read the active configuration and Flow2API image-model catalog, then require and lock `gemini-3.1-flash-image-portrait` into the configuration snapshot and generation plan. Set `executor` to `flow2api_mcp` and `prompt_language` to `en`. A `-2k` or `-4k` variant, a different model, or any other executor/prompt-language value is invalid for a storyboard-image Job.
2. Compile the generation plan from target-script Beat and target production Segment objects. Record target duration, the fixed production unit, each Segment's contiguous target time range and `candidates_per_segment`. Use the schema default of `2` unless the user explicitly overrides it. Each storyboard Segment must also declare concise `visual_continuity` plus exactly four static panel keyframes in reading order. Do not duplicate the semantic script merely to obtain more visual options; create A/B version records only after complete storyboard packages exist.
3. Map every script Beat to one or more storyboard panels; retain stable Beat, Line and Text IDs in the local package. For each panel, choose one frozen, directly observable instant and record its camera intent, inherited state and minimum human presence. Convert processes such as loading, pouring, opening, turning or dispensing into a decisive single-frame proof moment; never ask one panel to depict the whole process.
4. Prepare approved product, subject and routed reference images with `scripts/prepare_flow_inputs.py`. Expand all Segment attempts before submission. For the default 30-second plan, submit all six candidate Jobs through one `flow_submit_batch(kind="image")`, wait through `flow_wait_batch`, then retrieve each successful result. Increment `attempt` only for an intentional new visual candidate; reuse it for a transport retry. Capacity may split the stage into the fewest possible batches but never into an avoidable loop of single submissions.
5. Review each complete candidate's product action, state, continuity and timing, then run storyboard fidelity validation. Every Beat, key product action and assigned spoken line must have coverage. Confirm that each panel is an independently readable static moment, carried orientation/state is explicit, human visibility is no greater than planned, and no content crosses panel boundaries. Four panels do not imply four equal time windows; the locked target-script Beat timeline owns their exact timing. Reject the whole board when any panel makes it unusable; never crop or recombine panels.
6. Before image submission, write the exact script record's `分镜状态=生成中` and fresh-read it. After each candidate passes local validation, publish it to the backend `分镜候选` record with its Segment, attempt, run, Job and attachment identity. This table is an audit/staging surface, not the human approval surface. Local files are staging artifacts, never the cross-computer review surface.
7. Assemble one or more complete storyboard versions from the backend candidates. Each version must list every Segment in chronological order, identify the chosen candidate for each Segment, and pass a cross-Segment continuity review covering subject identity, room/light, product geometry, orientation, food state, action handoff and CTA closure. If no combination is independently coherent, regenerate the conflicting Segment; never ask the human to manually construct a version from loose boards.
8. Write each complete version to the script-version record with `脚本版本=A/B`, `完整分镜方案` attachments ordered by Segment, `分镜组合映射`, and `版本审核状态=待审核`. Fresh-read every version record and verify attachment identity, ordered count, source candidate IDs and continuity evidence. Machine checks are `视觉预检` only; they do not constitute final visual approval.
9. The human reviews the complete A/B version packages and approves at most one version per source script. Set the selected version to `版本审核状态=已通过` and the other to `未采用`; only the approved version may enter final-video production. Save the evidence to `plan/storyboard-writeback-verification.json` with `run_id`, source script record ID, version record IDs, ordered candidate mappings, observed attachment identities, observed statuses and verification time.

Stop before downstream final-video work if any required board, coverage or product-fidelity evidence fails, or if upload, script association, status write, attachment identity/count, or fresh-read verification fails. Resume the same run ID. A Flow2API health, catalog, submission, wait or result failure remains a resumable Flow2API failure; never retry it through GPT Image.
