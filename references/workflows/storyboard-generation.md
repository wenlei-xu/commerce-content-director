# Workflow: storyboard generation and script fidelity

Read authority.md, script-contract.md, script-validation.md, product-contract.md, subject-contract.md, product-execution-contract.md, reference-asset-contract.md, image-prompt-contract.md, [flow2api-image-execution.md](../flow2api-image-execution.md) and delivery-contract.md.

Input is one freshly read Feishu script record whose script status is locked and script check status is passed. Its `目标口播语言` and `structured_script.runtime.target_spoken_language` must both match `plan/language-lock.json`. A local script package alone is not sufficient. Read its structured script, accepted product assets, subjects and configuration. Never infer a different creative direction or rewrite the script.

Original and replication modes use the same output-production unit. Divide the locked target duration into configured 10-second target production Segments. Each target production Segment submits exactly one storyboard-image Job and returns exactly one 2×2 board containing four 9:16 panels. Therefore `storyboard Job count = target_duration_seconds / raw_segment_seconds`. Source-video narrative segments, selected evidence frames and reference timestamps do not alter this count.

1. Run the workflow-scoped preflight with the locked spoken language, fresh-read the active configuration and Flow2API image-model catalog, then lock the exact available model ID into the configuration snapshot and generation plan. Set `executor` to `flow2api_mcp` and `prompt_language` to `en`; no other values are valid for a storyboard-image Job.
2. Compile the generation plan from target-script Beat and target production Segment objects. Record target duration, the fixed production unit, each Segment's contiguous target time range and the exact expected Job count.
3. Map every script Beat to one or more storyboard panels; retain stable Beat, Line and Text IDs in the local package.
4. Prepare approved product, subject and routed reference images with `scripts/prepare_flow_inputs.py`. Submit, wait and retrieve each board only through the registered Flow2API MCP sequence defined by the execution contract.
5. Review product action, state, continuity and timing, then run storyboard fidelity validation. Every Beat, key product action and assigned spoken line must have coverage. Four panels do not imply four equal time windows; the locked target-script Beat timeline owns their exact timing.
6. Before image submission, write the exact script record's `分镜状态=生成中` and fresh-read it. After local fidelity review, upload every accepted board to that same record's `最终分镜图`, write `分镜状态=待审核`, `分镜审核意见`, and the script-derived `视频提示词` whose control instructions are English and whose spoken payload uses the locked language, then fresh-read the same record. Local files are staging artifacts, never the final storyboard delivery.
7. After user or authorized acceptance, write `分镜状态=已通过` on that same script record and fresh-read again. Verify the script record ID, attachment token/name/count, status, review notes, and video prompt against the current run. Save the evidence to `plan/storyboard-writeback-verification.json` with `run_id`, `script_record_id`, expected board count, observed attachment identities, observed status, and verification time. Only this verified state completes storyboard production.

Stop before downstream final-video work if any required board, coverage or product-fidelity evidence fails, or if upload, script association, status write, attachment identity/count, or fresh-read verification fails. Resume the same run ID. A Flow2API health, catalog, submission, wait or result failure remains a resumable Flow2API failure; never retry it through GPT Image.
